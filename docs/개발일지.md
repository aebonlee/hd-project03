## 1. 요구사항 분석

기획서의 핵심 흐름은 다음과 같다.

```
업체 실무자: 사업자번호 로그인 → 대여 아이템 실사 수량 입력 → 불일치 시 소명 필수
           → 삭제(대여 종료) 요청 → 실사결과 확인서 업로드 → 제출
HD 담당자: 제출 알림 수신 → 검토(장부 vs 실사, 소명, 첨부) → 삭제 요청 승인/반려
           → [리포트 요청] → 기존 보고 양식대로 보고서 자동 생성 (수량·금액 일치도 중심)
```

- 보안 중요도 낮음 → 사업자번호 + 비밀번호 수준 인증. 단 **업체 간 데이터 교차 노출 금지**는 필수.
- 기존 보고 양식 파일은 미확보 → 표지 요약 + 업체별 시트 구조의 샘플 양식을 자체 설계 (양식 확보 시 교체 가능).

## 2. 설계 결정

| 결정 | 이유 |
|---|---|
| 단일 페이지 웹앱 + localStorage 데모 DB | 개인 환경에서 서버 없이 전체 흐름 검증. GitHub Pages 배포 가능 |
| 역할 분리(업체 실무자 / HD 담당자)를 로그인 화면에서 전환 | 기획서의 두 사용자 유형을 한 앱에서 데모 |
| 비즈니스 로직을 `js/logic.js`(UMD)로 분리 | 권한 필터·제출 검증·일치도 계산을 Node에서 단위 테스트 |
| 알림은 알림 로그 + 어댑터 | 메일/문자 수단 무관이라는 기획 조건. 실연동(Resend/SMTP)은 README 안내 |
| Supabase 스키마(`supabase/schema.sql`) 동봉 | 실서비스 전환 시 Postgres + RLS(업체 격리) + 제출 검증 트리거로 즉시 이관 가능 |

## 3. 구현 내역

1. **업체 실무자 화면**: 사업자번호+비밀번호 로그인(데모 계정 표), 본인 업체 아이템만 표시(권한 필터로 격리), 실사 수량 입력 → 일치/불일치 자동 판정, 불일치 소명 미입력 시 제출 차단, 삭제(대여 종료) 요청, 확인서 업로드(10MB, PDF/JPG/PNG, 이미지 미리보기), 제출 → 담당자 알림.
2. **HD 담당자 화면**: 업체별 제출 현황 대시보드(미제출/제출/불일치 있음/승인 완료), 제출 상세 검토, 삭제 요청 승인/반려, 실사 승인, 제출 독려 알림, 알림 로그, 기준 데이터(업체/아이템) 엑셀 임포트·내보내기.
3. **보고서**: SheetJS 엑셀 생성 — 표지 요약(전체 수량 일치도 %, 금액 일치도 %, 불일치 건수, 삭제 요청 내역) + 업체별 시트. 인쇄용 PDF 뷰(window.print) 병행.
4. **시드 데이터**: 업체 5곳, 업체당 아이템 10~14개, 불일치 3건·삭제요청 1건·승인 완료 1개사 포함. "데모 데이터 초기화" 버튼 제공.

## 2026-08-25 — 서버 연동 (업체별 격리) · 뷰가 RLS 를 우회하던 구멍

### 한 일

`js/supabase-store.js` 신설 — `js/store.js` 와 **같은 모양의 API** 를 Postgres 위에 올렸다.
화면(app.js)은 `Store` 하나만 보고 쓰므로 저장 위치가 바뀐 것을 모른다.

**문서 통째로 공유(hd-docsync)는 쓸 수 없었다.** 그 방식은 접속한 사람이 문서 전체를
받으므로 대한테크가 한빛물류의 실사 결과를 그대로 받게 된다.
행 단위로 담고, 격리는 **화면이 아니라 DB(RLS)** 가 한다.

로그인도 DB 가 판정한다 — 업체는 `사업자번호@도메인` 가상 이메일,
담당자는 실제 이메일. **관리자인지 아닌지는 `is_hd_manager()` 에게 묻는다.**
화면이 비밀번호를 비교하면 우회된다.

### ★ 뷰가 RLS 를 우회하고 있었다

가장 큰 발견이다. 표는 정책으로 잠갔는데 **보고서 뷰는 안 잠겨 있었다.**

PostgreSQL 의 뷰는 기본적으로 **만든 사람의 권한**으로 돈다.
그래서 뷰를 읽을 수 있는 사람은 밑에 깔린 표의 RLS 를 통째로 지나친다.

실측 — 한빛물류 계정으로 `report_vendor_summary` 를 읽으니
**대한테크의 수량·금액 일치도가 그대로 나왔다.** 이 포털의 목적이 무너지는 결함이다.

고친 방법: 모든 뷰에 `with (security_invoker = true)`.
**11개 프로젝트 35개 뷰 전부**에 적용했다 — 같은 틀로 만들었으니 같은 구멍이 있었다.

### 통합 테스트가 잡아낸 것 두 가지

1. **새 실사의 `id: null` 을 보내고 있었다.** 표는 `default gen_random_uuid()` 인데
   명시적 null 이 기본값을 덮어 `not-null constraint` 로 거부됐다. 키를 아예 빼야 한다.
   그리고 서버가 정한 id 를 **돌려받아 메모리에 붙여야** 이어지는 실사 상세가
   `audit_id` 를 제대로 들고 간다.
2. **담당자가 `audit_line` 에 upsert 하면 막힌다.** 정책상 INSERT 는 업체만(작성중일 때),
   담당자는 UPDATE 만 할 수 있다. upsert 는 `INSERT ... ON CONFLICT` 라 통째로 거부된다.
   그래서 **받아 온 행은 UPDATE, 처음 만드는 행만 INSERT** 로 나눴다.

### 검사 환경도 실제와 맞췄다

스텁이 함수 기본권한만 재현하고 **표·뷰 기본권한을 빼먹고 있었다.**
Supabase 는 표에도 기본 권한을 준다(접근 제어는 권한이 아니라 RLS 가 한다는 전제).
재현하지 않으면 "권한이 없어서" 막힌 것을 "정책이 막았다" 고 착각한다 — 반대도 마찬가지다.

RLS 를 **켠 채로** 검사하려고 `tests/fake-supabase.js` 에 가장 기능을 넣었다.
`set local role authenticated` + `auth.uid()` 를 그 사람으로 두면 정책이 진짜로 걸린다.
superuser 로 붙으면 RLS 가 우회되어 아무것도 증명되지 않는다.
